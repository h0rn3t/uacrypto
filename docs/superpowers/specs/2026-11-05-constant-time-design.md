# Реалізація за сталий час — проєкт

Дата: 2026-11-05. Пункт плану README «Реалізація за сталий час».

## Навіщо

Мета — зняти з README і godoc застереження про те, що за часом роботи можна відновити
приватний ключ, і щоб це було правдою, а не формулюванням. Швидкість поки не важлива.
Закрити пункт має перевірка, яку видно в GitHub Actions і яка **блокує реліз**.

## Цілі

1. Кожна операція, що торкається секрету, виконується без гілок і без звертань до пам'яті
   за адресою, яка залежить від секрету:
   - ДСТУ 4145: `GenerateKey`, `NewPrivateKey`, `Sign`, `PrivateKey.Bytes`, обчислення
     відкритого ключа з `d`;
   - Калина: розгортання ключа, `Encrypt`, `Decrypt` (а через них CMAC, GCM, CCM, XTS, wrap);
   - Купина: стиснення (дані хешу можуть бути секретом, наприклад ключ HMAC);
   - ГОСТ 28147 (і через нього ГОСТ 34.311): раунд.
2. Статистичний тест часу в стилі dudect у GitHub Actions. Він блокує реліз і має
   негативний контроль, тобто доводить, що здатен знайти витік.
3. README (розділ «Безпека» і пункт плану) та godoc `dstu4145` і `kalyna` оновлені.

## Не цілі

- Швидкість. Повний перебір таблиць і проста арифметика прийнятні, bitslice не робимо.
- Сталий час для операцій лише з публічними даними: `Verify`, `ParsePublicKey`,
  `PublicKey.Bytes`, `CurveFromParams`, увесь `pki` (розбір і перевірка). Їм достатньо бути
  правильними. Якщо вони спільно з секретними шляхами користуються новою арифметикою, це нормально.
- Захист від атак з фізичним доступом: енергоспоживання, ін'єкція збоїв.
- Затирання секретів у пам'яті (zeroization).
- Аудит. Фраза «код не проходив аудиту» і порада щодо сертифікованих засобів КЗІ лишаються в README.

## Анти-цілі (провал, навіть якщо «працює»)

- Зміна будь-якого вихідного формату або API: ті самі ключі, публічні ключі, шифротексти, геші,
  MAC. Наявні тести на векторах і `make -C parity` проходять без змін в очікуваних значеннях.
- CT-тест, який нічого не ловить (немає негативного контролю), або тест, який через шум
  раннерів падає на чистому коді й робить релізи лотереєю.
- Нова зовнішня залежність. Модуль лишається тільки на stdlib.

## Обмеження

- Go 1.27, лише стандартна бібліотека; `crypto/internal/...` недоступні.
- Гейт із CLAUDE.md: `gofmt`, `go vet`, `golangci-lint`, `go test -race -count=1 ./...`.
- CI вже проганяє `GOARCH=386 go test ./kalyna`. Код має бути правильним і на 32-бітних
  платформах (`math/bits` на `uint64` там працює; сталий час гарантуємо лише для 64-бітних).
- Коментарі й godoc англійською, README українською.

## Що вирішено

### ДСТУ 4145

Наявні вади: поле на `math/big` з гілками за бітами, `scalarMult` як double-and-add з
`if bit == 1`, інверсія Евкліда, `s = r·d + e mod n` через `big.Int`, `d` зберігається
як `*big.Int`. Через витік `e` ключ відновлюється за одним підписом, тож усе це в межах проєкту.

Рішення (це мій вибір, користувач делегував):

- **Поле GF(2^m)** на фіксованому масиві лімбів (`[7]uint64` покриває m ≤ 431).
  Множення без переносу виконується масками фіксовану кількість ітерацій, у стилі `kalyna/field.go`.
  Редукцію за поліномом кривої роблять зсуви на публічні m і k. Інверсія виконується
  піднесенням до степеня 2^m−2 (Ферма або Ітох–Цудзії). Кількість ітерацій залежить лише від m.
  Ця арифметика повністю замінює наявний `field` на `big.Int`: один код для всіх шляхів.
- **Множення точки на скаляр** реалізоване драбиною Монтгомері (López–Dahab, x-координата
  в проєктивних координатах, відновлення y наприкінці). Обмін робиться маскою (cswap),
  кількість кроків фіксована й залежить від довжини n, а не від скаляра. Провідні нулі
  скаляра не повинні впливати на час (наприклад, додати до скаляра n або 2n так, щоб старший
  біт був на фіксованій позиції).
- **Арифметика за модулем n** для `s = r·d + e mod n`: фіксовані лімби, множення й редукція
  без гілок за значеннями (наприклад, множення Монтгомері). `big.Int` у секретних обчисленнях
  не використовується.
- **Секрети в структурах:** `PrivateKey.d` зберігається у фіксованих лімбах або байтах, а не в `*big.Int`.
  Перевірка діапазону в `NewPrivateKey` виконується за сталий час.
- **Випадкові скаляри** (`GenerateKey`, разовий `e` у `Sign`): вибірка з відкиданням має
  рівномірний розподіл на [1, n−1]; порівняння з n виконується за сталий час. Кількість спроб може
  витікати, бо вона не залежить від прийнятого значення. Спосіб читання байтів з `random`
  може змінитися: тестів, які фіксують підпис за детермінованим джерелом випадковості, немає.
- **API на межі не змінюється:** `Sign` повертає `r, s *big.Int`, а `Verify` приймає їх
  (це публічні значення). Конвертація на межі допустима.
- `Verify` і `ParsePublicKey` можуть користуватися новим полем і драбиною, тоді зникне
  потреба тримати дві арифметики. Сталий час для них не вимагається.

### Калина й Купина (`internal/spn`)

- **S-блоки:** кожен пошук `Sbox[i][x]` і `sboxInv[i][x]` за секретним `x` замінюється
  повним проходом по 256 елементах із маскою рівності. Одна функція в `internal/spn`
  обслуговує обидва пакети.
- **`spn.Mul`:** зараз цикл іде за `b` (`for b != 0`), а `b` у `MixColumn` — це байт стану.
  Потрібні рівно 8 ітерацій з масками незалежно від значень.
- Множення в GF(2^n) для GCM (`kalyna/field.go`), `ConstantTimeCompare` для тегів і
  `subtle.XORBytes` уже працюють за сталий час, їх лише перевіряємо при ревʼю.

### ГОСТ 28147

- Пошук `sbox[i][nibble]` замінюється проходом по 16 елементах рядка з маскою.
  Додавання за модулем 2^32 і циклічний зсув уже працюють за сталий час.

### Перевірка часу (dudect) у GitHub Actions

- Тести за build tag (наприклад, `//go:build ctcheck`) не потрапляють у звичайний
  `go test -race ./...`.
- Для кожної секретної операції є два класи входів: **фіксований** секрет (вибраний так, щоб
  провокувати витік: малий скаляр, нулі, мала вага Геммінга) і **випадкові** секрети.
  Класи чергуються випадково, після кожного виміру часу обчислюється онлайн t-тест Велча
  (метод dudect: Reparaz, Balasch, Verbauwhede, 2017). Дані, які операція бачить окрім
  секрету (геш, відкритий текст), однакові в обох класах або однаково випадкові.
- Операції під тестом: `dstu4145.Sign` (окремо змінні `d` і `e`), обчислення відкритого
  ключа з `d` (`NewPrivateKey`), шифрування, розшифрування й розгортання ключа Калини,
  стиснення Купини, шифрування блоку ГОСТ 28147.
- **По одному представнику на механізм** (рішення користувача): крива M257, Калина-128
  (блок 16 байт), Купина-256. Решта кривих і розмірів блоку використовує ті самі функції поля,
  драбини й S-блоків, тож їх охоплюють ревʼю коду й тести правильності. Якщо прогін
  не вкладається в кілька хвилин навіть так, поступається перелік, а не поріг і не правило «без повторів».
- **Поріг:** |t| > 10 означає витік, тест падає. Повторних спроб немає.
- **Негативний контроль:** той самий харнес на навмисно змінночасовій еталонній операції
  (наприклад, нинішній double-and-add на `big.Int`, перенесений у тестовий файл, або
  `big.Int.Exp` зі секретним показником) **мусить** дати |t| > 10. Якщо не дає, тест
  падає: на цьому раннері перевірка нечутлива.
- **Де запускається:** у `.github/workflows/release.yml` як крок перед створенням релізу, тож
  падіння блокує реліз. Також `workflow_dispatch`, щоб прогнати вручну до тегу.
- Локальний запуск описаний у README (одна команда), щоб перевірити до пушу тегу.
- *(Мій вибір.)* Харнес від початку міряє пачку з кількох викликів на один замір і калібрує
  розмір пачки під роздільність годинника. На Apple Silicon годинник має крок близько 41 нс,
  а раунд ГОСТ коротший. Еталонна платформа — linux/amd64 у CI. Локальний запуск на
  darwin/arm64 корисний, але не обов'язковий: README прямо каже, що доказом є прогін у CI,
  і формулює гарантію як «перевірено на linux/amd64».

### Документація

- README, розділ «⚠️ Безпека»: прибрати «не виконується за сталий час» і «не для захисту
  бойових ключів»; написати, які операції працюють за сталий час, як це перевіряється
  (CT-тест у CI, що блокує реліз), що лишилося поза межами (фізичні атаки, аудит).
  Аудит і сертифіковані засоби КЗІ лишаються.
- Пункт плану отримує `[x]`.
- Godoc: прибрати «not constant-time» у `dstu4145` (пакетний коментар, коментар
  `scalarMult`) і «Nothing in this package is constant-time» у `kalyna`, написати, що за
  сталий час працює.

## Залишено будівельнику

- Конкретні алгоритми інверсії, редукції й модульного множення, якщо вони без гілок і
  звертань за секретом.
- Розкладка за файлами й пакетами (наприклад, окремий файл скалярної арифметики в `dstu4145`;
  чи виносити харнес dudect в `internal/`).
- Кількість вимірів і бюджет часу CT-тесту. Мета: на `ubuntu-latest` проходить чистий код і
  падає негативний контроль у межах кількох хвилин; підібрати на пробному прогоні через
  `workflow_dispatch`.
- Додаткові тести правильності нової арифметики: зовнішні вектори BC вже є; можна додати
  порівняння з поточною реалізацією на `big.Int` як тестовим еталоном.
- Порядок робіт. Розумно почати з ДСТУ 4145 (найбільший ризик), потім `spn`, ГОСТ, CT-тест, документація.
